No dependency added.

The new transaction owner implements **Wave 0 audit configuration only**. Its trusted business-owner adapter validates the command, reads and locks current actor/role/target/revision, and returns an immutable attribution grant plus a mutation closure that captures validated command primitives. That closure performs its revision and work-intent writes on the same transaction. Audit persistence and its operation receipt follow before COMMIT. External effects are prohibited inside this callback. The fixture owner uses actual PostgreSQL locks and current synthetic principals; it is not production identity or a deployed audit-settings workflow.

Producer namespace and environment come from installation composition, company/operation from the validated transaction, actor/configuration/revision from the owner, and event identity/time from the application. The existing Wave-0 serializer constructs bounded primitive JSON. There is no public prepare/append path that could persist success without running the complete operation. Both `fsync` and `synchronous_commit` must be on. The runtime role receives only SELECT/INSERT over event/receipt tables; schema ownership and migration privileges remain with deployment. Composite receipt constraints bind company, producer, operation and event. No UPDATE, DELETE, TRUNCATE or automatic expiry is granted.

No success is returned until COMMIT acknowledgment. Unknown acknowledgment retains the original operation identity for a fresh, current-authority receipt lookup. Reusing an operation cannot repeat its mutation. The receipt consumer returns only event identity and committed outcome, never the full audit record. This API does not accept transported events or implement standalone retransmission/conflict quarantine; #108 owns that distinct path. Required denied/failed/rolled-back audit delivery and independent health are still outstanding, so no product activation or full Wave-0 coverage is claimed.

## Implemented boundary

The former HTTP-only worker counter is replaced by one main-thread process owner in `src/workers/json-tasks.js`. It admits at most two workers and 100 pending tasks, with an additional conservative **16 MiB total pending input** cap. The byte cap prevents a queue of 100 maximum-size pages from retaining a gigabyte of raw input; it is a lower local admission limit, not permission to raise SEC-5 ceilings. A full pool rejects HTTP immediately without queuing its body. Job-oriented callers may queue; cancellation removes pending copies and debits immediately. New service replicas or another worker-creating entry point cannot assume this process-local state coordinates the installation: that requires separate composition/deployment evidence.

Admission checks precede copying. Each admitted input is copied once into an exact buffer; later caller mutation cannot alter the queued task and a buffer-pool neighbor cannot be transferred accidentally. On worker start that buffer is transferred, not copied again. Only bytes and reviewed numeric limits are sent to the fixed JSON worker. Environment and inherited CLI preloads are excluded; stdout/stderr are drained without forwarding raw worker output. The explicit empty `execArgv` also does not inherit a future parent permission profile: a compatible production profile remains release work, and this is not permission-model isolation evidence.

Code-owned parser limits can be lowered but cannot exceed 10 MiB input, depth 64, 100,000 entries or 2,000 ms; HTTP still uses 64 KiB. Repository owners must use their stricter 2 MiB file limit. The duplicate-aware JSON visitor retains poisoning, exact-number, malformed UTF-8/string and grammar checks. Worker old-generation storage is limited to 64 MiB. This is **not** a complete memory limit or hostile-code sandbox: ArrayBuffers, native allocations, the parent process and container limits remain separate. Only JSON syntax is implemented; adding XML/YAML/TOML/HTML/PDF workers requires the same shared admission owner plus each format's reviewed bounds and tests.

Each active task has a monotonic deadline and real worker termination. Delayed timer delivery cannot admit an overdue message; cancellation/deadline is checked again after termination, before returning a value. Capacity is released only after cleanup. Worker exceptions, malformed messages, early exits and termination errors become bounded categorical failures without raw payload/error text. Diagnostics expose aggregate counts only. These syntax results establish no authority: the use case must still recheck its current policy and durable attempt token at persistence/disclosure. There is no parser-side database commit.

## Job budget transition

`src/jobs/work-budget.js` supplies a pure transition for a **future durable owner**. It validates a closed loaded record and expected company/job/attempt/version, adds exact nonnegative decoded-byte/tree-entry/active-ms deltas, increments the version, and returns a new frozen record. It caps one repository job at 256 MiB decoded input, 100,000 tree entries and 900,000 active milliseconds. Mismatched fences, unsafe values, unknown/accessor fields, exhausted ceilings and attempts to subtract/reset fail closed without mutating the loaded record. Smaller code-owned limits are supported.

This function is not authentication, a lease check or persistence. The owner must load scoped state, verify current authority and lease, bind the fence/version predicate and persist counters atomically before admitting protected work. Retry/attempt renewal must retain the logical job's counters. Active time must be measured around owned work, excluding provider backoff and queue wait. A conservative pre-work debit may remain charged after uncertain/crashed work; no refund path is implemented here. The function does not invent zero counters, issue attempts, refund credits or reset history. Serialization/reload fixtures test exact transition data, **not** PostgreSQL restart/transaction behavior. The blocked persistence foundation in #92 and durable owner #93 remain necessary for those guarantees.

## Actual validation

Local macOS arm64, Node 24.16.0/npm 11.16.0: build, strict checked contracts, runtime/import guard, dependency/artifact checks, whitespace checks and npm audit pass (zero reported known advisories). The combined suite passes **67 tests**. Eleven new groups cover limit configuration, real worker syntax/entry/depth/byte boundaries, shared HTTP admission, count/byte saturation, cancellation, mutable queued buffers, timer congestion, worker faults and cumulative counter transitions. Worker-fault fixtures copy the actual owner unchanged into an isolated temporary tree and substitute only a fixed test module; the normal JSON tests use the actual production worker. The fault suite also observes 64 MiB old-generation configuration, an empty worker environment and no inherited CLI flags. Existing registered Fastify/native HTTP tests still pass through the shared worker owner.

The [retained local capacity record](evidence/parser-capacity-macos-2026-11-05.json) comes from `node integration/parser-capacity.mjs`: two 2 MiB inputs followed by 100 64 KiB inputs; 102 completed, the 103rd rejected; maximum two active and 100 pending, 6,553,600 pending bytes. Elapsed time was 993 ms on an Apple M5 Max/18 logical CPUs/128 GiB host. Observed RSS peaked at 125,632,512 bytes with 10 ms sampling; process-reported peak was 126,779,392 bytes. This synthetic parser-only measurement does not establish a minimum machine, throughput promise, production container memory limit or NFR-4.2's full 1,000-repository/100-user acceptance. The capacity script is added to selected Linux CI; that run is pending.

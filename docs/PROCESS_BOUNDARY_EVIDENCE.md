# REQ-PLATFORM-023 — process termination and admission

2026-11-05. Read the issue template, project-local secure-coding guide, SEC-1/3/5/8/9/10, SEC-068 and the Node.js process exception guidance before implementation. Node's [uncaught-exception warning](https://nodejs.org/api/process.html#warning-using-uncaughtexception-correctly) requires termination and an independent monitor; asynchronous recovery after a fatal exception is not safe.

The trusted composition capability installs once before serving. Uncaught exceptions, unhandled rejections (including strict mode), explicitly critical internal stream errors and startup failure exit immediately with fixed nonzero codes 70–73. Error objects, messages and stacks are never inspected or written. Exit status is the minimal bounded signal for an external supervisor. Ordinary request/provider socket failures do not become critical process errors.

SIGTERM/SIGINT and the local shutdown capability stop admission synchronously, abort active request ownership and drain owned resources for at most five seconds. Duplicate shutdown signals do not repeat cleanup. Failed cleanup exits 74; the deadline cancels its signal and exits 75. The HTTP factory rejects new work before authorization and blocks a late successful response after admission stops. There is no shutdown endpoint or caller-selected exit code. A blocked event loop, native crash or SIGKILL still requires an external supervisor; a JavaScript timer cannot enforce that boundary.

Six focused groups exercise real child processes and the production Fastify factory: exception/rejection/stream/startup termination, conflicting installation, actual repeated OS signals, successful graceful shutdown, synchronous admission and asynchronous drain failures, fatal failure during drain, a real five-second hung drain, active cancellation, denied new admission and suppression of late private response bytes. Child stdout/stderr must remain empty; the parent records exit status and enforces an independent test deadline. A separate build-guard group proves that process access is limited to direct, literal calls in the owning module; computed properties, environment/output access, aliases, arbitrary event listeners and other modules remain rejected.

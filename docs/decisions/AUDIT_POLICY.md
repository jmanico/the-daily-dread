# Audit policy selection — OD-001, OD-002 and OD-004

Decision date: 2026-11-05. Accountable project owner: Jim Manico. Selection prepared by Codex under the project lead's explicit instruction, “resolve the blocked decision as best you can and continue.” This delegates the project policy choice; it does not supply facts about an installed company system. This document selects the implementation contract for issues #28, #29 and #30. Company-specific activation evidence remains required by #23; no deployment, new external destination, human review or runtime coverage is claimed.

## OD-001 / #28: destinations, readers and independent health

Use the existing PostgreSQL database for authoritative audit records. Do not introduce a broker, external collector, SaaS telemetry account, email/SMS/chat forwarding, or a second logging library. The existing Fastify logger remains the structured operational logger. Security events pass the shared ledger projection before either audit persistence or any permitted operational projection.

| Consumer/destination | Permitted data | Access and ownership |
| --- | --- | --- |
| A: PostgreSQL append-only audit history | The exact validated versioned event envelope and only that event's declared additional fields. No request/error objects, raw rejected input or undeclared fields. | Project lead owns schema/policy. Runtime writer can insert through the audit adapter, with no update/delete or unrestricted history reads. Separately scoped query role supports current company admins; company and current role checks occur before reads and immediately before disclosure. Company IT owns migration, backup and recovery credentials outside the application. |
| H: admin health view | Fixed state/reason codes, observation time, queue depth, dropped/unrecorded counts and lag; no actor/target/recipient references or event bodies. | Current company admins. Health query role reads only the bounded health projection, not the event table. IT's independent monitor uses its own restricted identity and cannot read business/audit bodies. |
| P: existing product status/history | The owning workflow's existing authorized minimal projection. | Existing company/owner authorization. P does not grant access to the audit table or forward the security stream. |
| Local Fastify stdout/stderr | Code-owned component/route-template, status/category, bounded duration/count, server request correlation where already permitted by SEC-8. Security-pipeline diagnostics use only fixed stage/code/count/lag fields; no full audit-event copies or actor/target references. | Docker's local logging driver on the company host, accessible only to company IT's host/container operators. No application Docker-socket mount. Retention is below. |

For applicable ledger rows with U, the selected default investigation consumer is A, with only an H aggregate exposed for pipeline faults. This resolves consumer assignment, not the missing signal: unavailable_signal rows remain unavailable, and reserved names do not authorize a detector or provider feed. A/H/P meanings and field exclusions remain binding. Tenant routing comes from authenticated application/installation context. Unknown callers do not acquire a tenant from submitted fields; inaccessible targets are omitted, never looked up merely to enrich a denial. No cross-installation aggregation is selected.

Independent health is a separately supervised local monitor process with read-only access to a fixed-size application heartbeat and a narrowly granted database probe/checkpoint view. It must not run in the application's event loop or depend on the Fastify sink it observes. The application heartbeat contains only a monotonic sequence and bounded fixed-category counters, never events. The monitor verifies heartbeat advancement and collector checkpoint progress separately from database availability. Probe writes, if needed, use a dedicated synthetic probe table, not fabricated business audit events. The monitor exposes its own health/exit status to the company supervisor. No notification recipient or successful operator delivery is assumed.

Before activation, company IT must bind these role names to actual operators/credentials, provide protected storage/mount/network configuration and the supervisor's observable failure consumer, and demonstrate denied access plus a stalled/dead application and unavailable database. Same-host supervision does not detect total host loss; installation monitoring/recovery must cover that separately. Missing assignments prevent activation, not implementation/testing of this selected local contract with synthetic identities. No deployment policy may silently expand a field subset or destination. Operational logger delivery must use a separate nonblocking bounded adapter: at most 32 pending records and 128 KiB, with a 4 KiB diagnostic-record cap. Saturation discards only these non-audit diagnostics with a health counter; it cannot sample or discard the authoritative audit path. A blocked stdout consumer cannot block the event loop or business response. Actual stream/callback timeout and shutdown behavior requires a controlled sink test, not merely a queue-length assertion.

## OD-002 / #29: retention, copies and disposal

Keep FR-11.1: authoritative audit history has no automatic expiration. This selection avoids inventing a short audit-retention period. It accepts ongoing storage/backup cost, which must be measured before activation; disk pressure never authorizes deleting required history.

| Copy class | Selected lifecycle |
| --- | --- |
| PostgreSQL audit history and replicas | No automatic expiration or application delete privilege. Replica lifecycle changes must preserve a verified authoritative copy and follow company IT recovery controls. |
| Audit-containing backups and administrative investigation copies | No automatic disposal in the project profile. Company IT must inventory and protect them in company-controlled storage. A later shorter lifecycle requires an explicit owner policy amendment and recovery/legal-hold review; it cannot be inferred from this decision. |
| In-memory delivery buffers | Bounded as OD-004; removed after confirmed commit or terminal failure. They are not durable history. Process-crash loss is explicitly possible before commit. |
| Disk spool / external collectors | Not selected. Do not create a fallback file containing audit events or add a forwarding destination. |
| Invalid/unknown-schema input | Never retain raw input. Record only a fixed safe rejection code/count through independent health. Valid same-ID conflicts retain the two separately validated projections in an access-restricted conflict table without expiration; never overwrite the original or treat a conflict as success. |
| Local operational diagnostics | Docker `local` driver with `max-size=10m`, `max-file=3`, compression enabled, per container. Oldest files rotate out by size; this is not a guaranteed number of days. No audit record may depend on this rotating copy. Inspect logs through Docker interfaces, not its internal files. |
| Server-generated downloadable output | Existing FR-4.7/SEC-5 rules: current authorization, removal on completed transfer/invalidation or 15 minutes after generation, whichever occurs first. Retained source/report/audit history remains independent of temporary output. |
| User-downloaded or support copies | No automatic upload or support-bundle collection. The deployment owner must assign custody and applicable hold/disposal handling before allowing this workflow. Application expiry cannot delete an already downloaded file. |

Residency is company-controlled installation storage only; no geographic location is asserted. Company IT must record actual host, replica, backup and download destinations, applicable hold requirements and storage capacity before activation. A hold requiring preservation of normally rotating diagnostics requires a separately approved, bounded preservation destination before enabling that collection; do not silently disable bounds or promise preservation the deployment cannot provide. No claim of legal compliance follows from this engineering policy.

## OD-004 / #30: obligations and failure boundaries

For implemented, applicable catalog events, `audit_required` is true except `dread.audit.health` and `dread.audit.validation_failure`, whose independent bounded health projections are false to avoid recursive audit failure. This is a catalog decision, never a request parameter. Unavailable/reserved events are not emitted. Existing mandatory audit classes remain mandatory, including authentication/access denials and failed or rolled-back attempts; frequent denials are not sampled. The two health exceptions do not exempt an underlying business operation's required audit. AI egress remains blocked by OD-005 until its digest representation is resolved.

- Administrative mutation, configuration revision, audit and work intent remain one transaction on one checked-out client. Require PostgreSQL `fsync=on` and `synchronous_commit=on`; no success before commit acknowledgement. Failure rolls back the mutation. Database/server/storage guarantees must be verified separately; this is not zero-loss or database-admin tamper resistance.
- A denied, failed or rolled-back operation records its outcome in a separate short audit transaction after any business rollback, using the same immutable event ID for identical retransmission. Preserve the original denial/failure; audit unavailability must never turn it into success or permission to proceed. Before a successful authentication, required audited disclosure/export, or other protected effect, commit the required audit/intent at its specified owner boundary. If that commit cannot be established, return a safe unavailable/unknown result and do not authorize the effect.
- Outbound effect intent remains durable before sending. If the result write fails after a possible send, retain unknown state for reconciliation; never claim failure means unsent or retry under a new logical identity. Durable owners retain their existing retry/fencing budgets.
- Audit append admission allows at most two active standalone writes and 128 pending immutable records, with a combined pending byte cap of 1 MiB. The 8,192-byte per-record limit still applies. Transactions belonging to a business commit use their owner's existing admission/deadline and cannot escape those bounds by spawning another writer. Standalone append has a 1,000 ms total deadline and at most one retry within it, only for a classified transient error and the same event. These are conservative starting limits to validate under load, not measured capacity claims.
- On unavailable storage, full queue, invalid required fields or deadline, mark the event unrecorded/unknown in bounded health counters and stop admission of new protected operations requiring audit. Already denied requests remain denied; there is no unbounded wait or recursive logger fallback. In-flight owners must recheck admission before an effect and retain transactional audit enforcement. Recovery requires a successful independent storage/pipeline probe and successful drain; a timer alone cannot restore readiness. An overflowing or crashing process can lose uncommitted denial/failure evidence. This residual loss is accepted for the bounded design, is visible as a gap, and must not be described as durable receipt.
- Deduplicate only an exact immutable projection under authenticated producer namespace + event ID. A valid conflicting projection is a protocol fault: reject the append, preserve both safe versions in restricted conflict storage if available, and mark unhealthy. Never persist raw malformed input in quarantine. Unavailable conflict storage follows the same unrecorded/fail-closed admission rule.
- Stop new admission on shutdown, drain for at most five seconds, then terminate nonzero when required appends remain. The process can lose its bounded in-memory records on forced termination. Durable intents survive only under the verified database/restore contract. Startup runs storage and pipeline checks before protected admission.
- Emit/update bounded heartbeat state every 10 seconds. The independent monitor polls every 10 seconds, uses a two-second probe deadline, and marks health failed when heartbeat/checkpoint evidence has not advanced for 30 seconds while active or queued work is pending, or immediately on an observed terminal fault. Healthy idle is established by advancing heartbeat/probe evidence, not by absence of events. Monotonic elapsed-time checks govern silence; wall-clock correctness remains the separate SEC-087 deployment gate. Monitor shutdown/failure must itself be observable through the supervisor, not the failed application sink. With a 10-second poll and two-second probe budget, the silence acceptance deadline is 42 seconds after the last observed advance, not a claimed 30-second end-to-end alert. Sequence reset/restart is a discontinuity: report unknown loss until startup storage/pipeline checks complete; zero counters after restart do not prove zero prior loss.

The bounds above select behavior under the delegated decision. They are not claims that PostgreSQL, a collector, a supervisor or the current app implements it. They must pass Wave-0 emission/consumer, outage/full/slow sink, crash/restart, rollback, conflict, tenant isolation and secret-canary tests before later instrumentation. Passing serialization alone cannot close #106.

## Alternatives and consequences

External collection could improve host-loss visibility but adds an unapproved destination, access and retention burden; it is not selected. A durable local disk spool adds recovery, encryption, disposal and duplicate reconciliation surfaces; use the existing database instead. Pure stdout audit cannot meet atomic mutation/audit requirements. Unbounded buffering avoids neither finite memory nor crash loss. Retaining all required audit events increases storage and denial-load pressure; bounded admission and explicit unrecorded health are required, never silent sampling.

The profile intentionally does not resolve the PostgreSQL package findings, TOOL-003, actual deployment identities, SEC-087 signals, AI digest schema, or independent human review. Those remain separate work. No event ledger evidence status changes from this policy selection.

## Local launch authorization

A public demonstration may continue to show public/synthetic records. It must never acquire access to the private local workspace by virtue of being on loopback. The private local application must implement and test this distinct profile before exposing protected data:

1. The trusted local launcher runs as the intended OS account, checks the private state root's ownership/mode and active listener, and provisions a stable opaque actor/workspace independently of browser input. No privileged daemon, remote administration or trust in a submitted OS username is selected.
2. A local unlock command generates a 256-bit random, single-use launch code with a 60-second lifetime, bound to the current process generation. Deliver it only through an explicitly requested interactive terminal/owner-only control channel; never normal logs, URLs/fragments, command-line arguments, environment variables, repository files, clipboard automation or external tools. Refuse noninteractive credential output. Only one pending code is allowed; issuing another invalidates the old code.
3. The browser exchanges the code by an exact same-origin JSON POST, with bounded parsing and rejection of cross-site, missing/null/wrong Origin, credentials in cookies, unsupported methods/fields and replay. Maximum five failed exchanges per minute for the entire local instance; no user-selected rate-limit key. This endpoint creates a session only, never configuration or business effects. A generic HTTP setup/admin endpoint remains prohibited.
4. The server returns a separately generated opaque 256-bit session secret once. Keep its digest and authority server-side, and its raw value only in the current page's memory. Every protected request carries it explicitly in Authorization; reject cookies and mixed credentials. No localStorage/sessionStorage/IndexedDB/service worker/token-in-URL storage. Refreshing or reopening the page requires another local unlock; do not invent a persistent browser credential to avoid that inconvenience.
5. Preserve 30-minute idle/eight-hour absolute limits, with background polling unable to extend idle time. Revoke on logout, server restart, restore, local actor/configuration change or detected clock rollback; clear private views and cancel in-flight work. Check current scope and revision at each use case/commitment point. Local identity does not grant unbounded filesystem/provider authority.
6. High-impact configuration/credential/restore actions require a fresh single-use local authorization bound to the session, operation, target and revision. No cached login or caller-provided timestamp is fresh authorization. The independent audit/recovery requirements still apply.
7. Reject non-loopback listeners and all remote/proxied modes at startup. This profile permits unencrypted HTTP only between this browser and literal loopback on the same trusted machine. Outbound HTTPS and database TLS verification remain mandatory. Enabling another network surface requires a separate reviewed profile, not a configuration flag that disables these guards.

This is an explicit specification change to FR-7's OIDC-only authentication and cookie-session selection **only for LOCAL-1**, not an OIDC fallback or an emergency account in a hosted installation. It introduces no password database, password recovery, anonymous private access or inferred Google/company authorization. The security boundary trusts the operator's OS account: same-account malware, a compromised browser/extension, or a privileged host can steal local credentials/data. Loopback and FileVault do not establish isolation from those principals. These limits must be stated in local operation instructions and tested where controllable.
